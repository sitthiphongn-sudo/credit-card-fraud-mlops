## 1. ปัญหาและผู้ใช้

| หัวข้อ | รายละเอียด |
|---|---|
| ปัญหา | ธุรกรรมทุจริตมีน้อยมาก (0.17%) แต่แต่ละรายการที่หลุดรอดทำให้เสียเงินจริง ต้องให้คะแนนความเสี่ยงของธุรกรรมทันทีที่เกิดขึ้น |
| ผู้ใช้หลัก | ธนาคารผู้ออกบัตร และทีมตรวจสอบ fraud ที่รับรายการที่ระบบแจ้งเตือนไปตรวจต่อ |
| ผู้ได้รับผลกระทบ | ลูกค้าเจ้าของบัตร (ถูกโกง หรือถูกระงับบัตรผิด), ทีมวิศวกรที่ดูแลระบบ |

## 2. ผลเสียเมื่อทายผิด

| ความผิดพลาด | ผลเสีย |
|---|---|
| False Negative (ทุจริตแต่ระบบปล่อยผ่าน) | ธนาคารเสียเงินเท่ากับยอดที่ถูกโกง (`Amount` ของรายการนั้น) |
| False Positive (ปกติแต่ระบบแจ้งเตือน) | ค่าตรวจสอบ 1.31 EUR ต่อรายการ และลูกค้าถูกระงับบัตรผิด เสียความพึงพอใจ |

ต้นทุนสองฝั่งไม่เท่ากัน จึงไม่ใช้ threshold 0.5 ตามค่าเริ่มต้น แต่เลือก threshold บนชุด validation
ให้ precision ≥ 0.80 ได้ค่า **0.51**

## 3. ทำไมต้องใช้ ML แทนกฎ

เทียบบนชุด test (ผลจาก `reports/experiments/`):

| วิธี | PR-AUC | Recall | เงินที่ประหยัดได้ |
|---|---|---|---|
| กฎ: แจ้งเตือนเมื่อยอดเงินสูงกว่า percentile 99.5 (`rule_amount_p995`) | 0.0014 | 0.000 | **−149.88 EUR** (ขาดทุน) |
| ML: `lightgbm_none` | 0.796 | 0.733 | **5,042 EUR** |

กฎจากยอดเงินจับทุจริตไม่ได้สักรายการ แต่ยังแจ้งเตือนรายการปกติที่ยอดสูงจนเสียค่าตรวจ
**แย่กว่าไม่มีระบบเลย** เพราะการโกงส่วนใหญ่ไม่ได้ใช้ยอดเงินสูงผิดปกติ
รูปแบบการโกงซ่อนอยู่ในความสัมพันธ์ของหลายฟีเจอร์พร้อมกัน ซึ่งกฎที่เขียนด้วยมือจับไม่ได้

## 5. ข้อมูลและ drift ที่คาดไว้

| หัวข้อ | รายละเอียด |
|---|---|
| แหล่งข้อมูล | ULB Credit Card Fraud (ธุรกรรมบัตรในยุโรป ก.ย. 2013) สัดส่วนทุจริต 0.17% |
| ฟีเจอร์ | `Time`, `Amount`, `V1`–`V28` (ผ่าน PCA มาแล้ว ตีความเชิงธุรกิจไม่ได้) |
| การแบ่งข้อมูล | เรียงตามเวลา 60/20/20 เพื่อจำลองการทำนายอนาคตจากอดีต |
| Data drift ที่คาด | พฤติกรรมการใช้จ่ายของลูกค้าเปลี่ยน เช่น ยอดเงินหรือช่วงเวลาที่ใช้บัตรเปลี่ยนไป |
| Concept drift ที่คาด | ผู้โกงเปลี่ยนรูปแบบ ทำให้ความสัมพันธ์ระหว่างฟีเจอร์กับการทุจริตเปลี่ยน recall ตกลงจาก baseline 0.733 |

## 6. ความเร็วและปริมาณ

ให้บริการแบบ**เรียลไทม์ทีละรายการ** ผ่าน API เพราะต้องตัดสินก่อนอนุมัติธุรกรรม
การรันแบบ batch จะรู้ผลหลังเงินถูกโอนไปแล้ว

## 7. การย้อนกลับเมื่อโมเดลมีปัญหา

| กลไก | หน้าที่ |
|---|---|
| Gate | ตรวจ gating metric ทุกข้อก่อนเลื่อนโมเดลใหม่เป็น champion ไม่ผ่านก็ไม่ขึ้นใช้งาน (ยังเก็บไว้เป็น challenger) |
| Registry alias | API โหลดจาก `models:/fraud-detector@champion` เสมอ เปลี่ยนโมเดลได้โดยไม่แก้โค้ด |
| Rollback | ย้าย alias `champion` กลับไปเวอร์ชันก่อนหน้า threshold ย้อนตามเองเพราะอ่านจาก run ของ champion |
